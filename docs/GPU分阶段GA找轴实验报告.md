# GPU 分阶段 GA 找轴实验报告

## 1. 实验目的

测试如下策略是否能加速磁轴搜索：

```text
阶段 1: 256 点群，fp32 粗搜
阶段 2: 达到某个残差阈值后，切换到 64 点群，mixed64 细搜
阶段 3: 用 fp64 blockline 对最终点做复核
```

其中 `mixed64` 指 $B$ 用 fp32，RK4 状态用 fp64。

实验参数：

```text
segments_per_coil = 256
steps = 800
coarse population = 16 x 16 = 256
fine population = 8 x 8 = 64
coarse precision = fp32
fine precision = mixed64
threads_per_line = 256
```

对照组是当前默认：

```text
mixed64 + 256 点群
```

## 2. 直接按 $10^{-4}$ 切换

| case | 方法 | 是否收敛 | 最终 mixed 残差 | fp64 复核残差 | GA 时间 | 粗搜/细搜代数 |
|---|---|---|---:|---:|---:|---:|
| `01/raw` | baseline mixed64 256 | 是 | `9.352e-09` | `1.737e-08` | 0.558 s | 0/0 |
| `01/raw` | fp32 256 到 `1e-4`，再 mixed64 64 | 是 | `4.929e-09` | `1.660e-08` | 0.450 s | 11/7 |
| `debug/raw` | baseline mixed64 256 | 是 | `2.007e-09` | `9.789e-09` | 0.718 s | 0/0 |
| `debug/raw` | fp32 256 到 `1e-4`，再 mixed64 64 | 否 | `4.465e-07` | `4.520e-07` | 2.452 s | 4/65 |

结论：

1. `01/raw` 上这个策略有加速，约 $19\%$。
2. `debug/raw` 上 `1e-4` 切换太早，64 点群进入细搜后卡在错误局部区域附近，增加细搜代数也不能解决。
3. 因此 `1e-4` 不适合作为默认切换阈值。

## 3. 更严格切换阈值

对 `debug/raw` 继续测试：

| 方法 | 是否收敛 | 最终 mixed 残差 | fp64 复核残差 | GA 时间 | 粗搜/细搜代数 | 切换时残差 |
|---|---|---:|---:|---:|---:|---:|
| baseline mixed64 256 | 是 | `2.007e-09` | `9.789e-09` | 0.718 s | 0/0 | - |
| switch `1e-5`, keep 8 | 否 | `4.465e-07` | `4.520e-07` | 3.611 s | 4/97 | `2.446e-06` |
| switch `1e-6`, keep 8 | 是 | `1.176e-09` | `1.454e-08` | 0.589 s | 9/10 | `8.699e-08` |
| switch `1e-4`, keep 16 | 是 | `2.391e-09` | `1.296e-08` | 0.644 s | 4/15 | `2.446e-06` |

这里有两个有用结论：

1. 对 debug，单纯把 fine 最大代数提高不能修复 `1e-4` 切换；问题不是代数不够，而是切换太早导致 64 点群信息不足。
2. 把切换阈值收紧到 `1e-6` 后，64 点群细搜可以稳定收敛，并且比 baseline 快约 $18\%$。

对 `01/raw` 的 `1e-6` 结果：

| 方法 | 是否收敛 | 最终 mixed 残差 | fp64 复核残差 | GA 时间 | 粗搜/细搜代数 | 切换时残差 |
|---|---|---:|---:|---:|---:|---:|
| baseline mixed64 256 | 是 | `9.352e-09` | `1.737e-08` | 0.558 s | 0/0 | - |
| switch `1e-4`, keep 8 | 是 | `4.929e-09` | `1.660e-08` | 0.450 s | 11/7 | `4.232e-05` |
| switch `1e-6`, keep 8 | 是 | `7.372e-09` | `1.459e-08` | 0.418 s | 14/4 | `7.824e-08` |
| switch `1e-4`, keep 16 | 是 | `2.121e-09` | `1.690e-08` | 0.513 s | 11/9 | `4.232e-05` |

`01/raw` 上 `1e-6` 反而更快，因为 fp32 粗搜虽然多跑了几代，但每代便宜，并且切换后 fine 阶段只需要 4 代。

## 4. 为什么 64 点群没有 4 倍加速

从单代时间看：

```text
mixed64 + 256 点: 约 0.043-0.048 s / 代
mixed64 + 64 点:  约 0.031-0.036 s / 代
fp32 + 256 点:    约 0.021-0.025 s / 代
```

64 点群的 mixed64 细搜只比 256 点群快约 $25\%$，不是 $4\times$。原因是 64 条线时 GPU 并行度明显不足，kernel 固定开销、block 调度和同步开销占比变高。也就是说，减小点群能省计算，但不能线性省时间。

真正贡献较大的加速来自粗搜阶段使用 fp32。

## 5. 结论

这个思路可行，但需要修改切换阈值：

```text
不推荐: fp32 256 到 1e-4 后切 mixed64 64
推荐:   fp32 256 到 1e-6 后切 mixed64 64
```

推荐配置：

```text
--staged
--coarse-precision fp32
--fine-precision mixed64
--switch-tol 1e-6
--fine-grid 8
--fine-keep 8
--fine-max-generations 96
```

这个配置在两个测试例子上都收敛：

| case | baseline 时间 | staged 时间 | 加速 |
|---|---:|---:|---:|
| `01/raw` | 0.558 s | 0.418 s | 1.33x |
| `debug/raw` | 0.718 s | 0.589 s | 1.22x |

由于加速幅度中等，而且阈值对稳定性敏感，当前建议是：

1. 保留 staged GA 为可选模式。
2. 默认仍使用单阶段 `mixed64 + 256`，因为它更简单、鲁棒。
3. 在批量评估很多线圈时启用 staged 模式，推荐 `switch_tol=1e-6`。
4. 最终报告的磁轴残差仍用 fp64 blockline 复核。
